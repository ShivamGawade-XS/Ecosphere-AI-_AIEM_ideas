# EcoSphere AI — Current Features and Expansion Backlog

**Status date:** 25 August 2026  
**Scope:** Locally verified repository capabilities, current product boundaries, and the next evidence-led improvements.  
**Primary SDG:** SDG 13 — Climate Action. **Supporting SDGs:** 7, 9, 11, and 12.

> EcoSphere AI is currently a **multi-tenant, evidence-led sustainability operations prototype**. Its numerical authority is deterministic server code; simulated records, scenario results, forecasts, factor use, and pilot disclosures are deliberately separated. It is not a live campus telemetry deployment, certified carbon-accounting platform, or activated production scheduler.

## Current Product Capabilities

| Product area | Available now | What makes it functional | Current boundary |
|---|---|---|---|
| **Tenant foundation** | Organizations, site registry, meters, memberships, owner/manager/operator controls, tenant audit events | Protected tRPC procedures enforce tenant scope and mutation roles | Invitation delivery, lifecycle/offboarding, SSO policy, and site-scoped roles need external identity work |
| **Reading intake** | Canonical manual-reading ingestion, source/unit/provenance records, retry-safe idempotency, protected data intake UI | Server validates active meter, unit, tenant, source, and idempotency before persistence | Manual generic intake correctly blocks simulated sources; live connectors remain unconfigured |
| **CSV data quality** | CSV parse/preview, valid/invalid rows, quarantine, idempotent commit, corrections, source/import lineage | Quarantined evidence is excluded from future analysis and corrections supersede rather than overwrite raw readings | No scheduled external file pickup or utility-provider connector |
| **Factor governance** | Versioned emissions factors, approval state, factor disclosure, pilot fallback boundary | Carbon values retain calculation/factor information | Not certified Scope 1/2/3 accounting or a complete regional factor library |
| **Monitoring worker** | Browser-independent deterministic worker, one-shot CLI, protected manual run, idempotent run keys, monitoring run records | Quality, carbon, anomaly, alert, EcoScore, forecast, and recommendation stages persist results | The recurring production scheduler is intentionally inactive |
| **Data-quality and anomaly logic** | Required-value/unit/future-date checks, rolling baseline deviation, anomaly/alert persistence, acknowledgment and recovery states; tenant resource rule profiles for high-value ceiling and future-timestamp tolerance | New monitoring evaluations record the active rule-profile ID/version in finding details; historical findings are not rewritten | Not equipment diagnosis, causal root-cause analysis, a calibrated ML model, or retroactive data correction |
| **EcoScore and targets** | Persisted 0–100 EcoScore snapshots with protected quality, anomaly, and carbon-trend component explanation; targets for energy/water/waste/carbon/EcoScore, UTC windows, freshness and attainment | Score, component explanation, and target calculations are server-owned and preserve explicit no-score/missing-component boundaries | Pilot methodology and weights require institutional validation; it is not a certified ESG rating, causal diagnosis, live-data guarantee, or reporting assurance |
| **Forecasting** | Moving-average and last-value candidates, rolling-holdout MAE selection, persisted method/rationale | Method choice and insufficiency state are transparent | No weather, occupancy, timetable, seasonality, or forecast confidence intervals |
| **Recommendations** | Deterministic anomaly recommendations with evidence, severity-tier confidence basis, limitations, impact disclosure, action handoff | Recommendations reference persisted anomalies, factors, forecasts, scenario/comparison context | It is evidence-linked rule support, not autonomous AI diagnosis or a savings guarantee |
| **Guided Campus Demo** | Explicit simulated baseline fixture, bounded cycles, controlled HVAC spike, pipeline refresh, alert/recommendation path, safe reset | Demo-only evidence is isolated and resettable | Requires deployed tenant/OAuth validation before it can be called a production demo service |
| **What-If Scenarios** | Server-authoritative energy/water/waste/renewable/recycling/investment scenarios, before/after results, ROI/payback, SDG mapping | Inputs, calculation version, outputs, and factor boundary persist with saved scenarios | Cost/tariff assumptions are pilot inputs, not procurement or realized savings |
| **Scenario sensitivity analysis** | Conservative/base/favorable ranges for explicit delivery performance, capex, tariff, and carbon-factor multipliers | Server returns the displayed case inputs with annual modeled savings, carbon reduction, ROI, and payback ranges | Ranges are not probabilities, forecasts, procurement quotations, certified factors, or realized outcomes |
| **Scenario Methodology Drawer** | Protected display of calculation version, exact pilot factors, formulas, sensitivity mechanics, and limitations | The drawer receives its disclosure payload from the same server domain that calculates scenarios | Pilot factors remain prototype defaults rather than official regional factors, procurement quotes, certification, or realized savings |
| **Operational Baseline Manager** | Accepted/non-superseded meter-window aggregates, reading count, latest evidence timestamp, simulated marker, server-verified scenario references | A saved baseline can apply only to its matching resource input and cannot be forged in preview/save calls | It is a user-chosen model input, not automatic annualization or an institutional baseline methodology |
| **Outcome measurement** | Completed action + saved scenario + exact operational baseline + same-duration accepted-reading outcome window, locked once recorded | The server compares observed aggregate change with the saved model, preserves reading counts/windows, and labels simulated evidence | The result explicitly does not prove causation, certified reduction, realized savings, or financial performance |
| **Intervention comparison** | Saved scenario comparison, transparent weighted components, disclosed templates, recommendation/action linkage | Ranking logic and components are inspectable | No sensitivity range, portfolio optimizer, or configurable institutional weighting policy |
| **Portfolio optimizer** | Bounded selection of two to ten saved tenant scenarios against an explicit modeled budget, maximum intervention count, and carbon-reduction or annual-savings objective | A protected server selector returns selected and excluded scenarios, modeled totals, deterministic tie-breaking, and scope limitations | It does not validate dependencies, shared/overlapping baselines, stacking, implementation feasibility, procurement, funding, realized savings, or carbon outcomes |
| **Actions and evidence** | Accountable actions, governed member assignment, approval evidence, status changes, required completion evidence, comments, attachments, scenario/comparison attribution, and explicit UTC-end-of-day target dates | Assignment and approval are tenant-scoped, manager/owner-gated, audit-recorded, and visibly distinguished from routing, funding, notifications, or delivery | No automated routing, funding workflow, calendar integration, external reminder, or workflow-automation claim |
| **Reports and traceability** | Stored evidence snapshots, executive evidence view, JSON/CSV export, print, selection-bound disclosure, methodology appendix, and intelligence timeline | Export and appendix are tied to persisted snapshot data rather than client recalculation | Not certified reporting, signed approval, or board-ready report production |
| **Operations and health** | Liveness/readiness endpoints, request IDs, CSP/HSTS in production, monitoring health, recovery states, scheduler-trial planner | Local production start and one-shot worker have been verified | No deployed restore rehearsal, active scheduler, or managed alert-delivery provider |
| **Meter Freshness Board** | Latest accepted, non-superseded evidence for every active tenant meter with fresh, aging, stale, or no-evidence status | Server derives data age and returns its evidence-cadence boundary with the latest timestamp | It measures stored evidence age, not live IoT connectivity, feed completeness, or sensor-health certification |
| **Maintenance windows** | Tenant-scoped, meter-specific UTC work intervals that suppress matching alert creation | The worker retains readings and anomaly evidence, writes a suppression audit linkage, and visibly lists the time-bounded window | It does not suppress quality findings, score effects, recommendations, evidence retention, or unrelated meters; it is not a maintenance-management system |
| **IoT security foundation** | Device registration, credential rotation, tenant/meter binding, sequence/idempotency, skew and rate validation | Telemetry ingress is designed for controlled authenticated device input | No live gateway, hardware calibration, MQTT/BMS adapter, or campus device pilot |
| **Public narrative** | Responsive Field Operations Ledger story, explicit simulation boundary, intervention selection and protected-workspace handoff | Public page no longer emits divergent client-side CO2/savings/ROI numbers | It cannot substitute for a configured authenticated workspace demonstration |
| **Workspace discovery** | Interactive public ecosystem directory at `/explore`, category filters, ten workspace capability cards, selected-workspace detail, and explicit authenticated handoffs | Visitors can discover each protected operational surface and its claim boundaries before a tenant session is created | It describes protected capabilities but does not expose tenant records, controls, simulation state, or replace authenticated use |
| **Authenticated quick navigator** | Searchable cross-workspace navigator available from the shell and Ctrl/⌘ K | Keyboard and pointer users can filter the actual route catalogue and open a selected workspace directly | It contains only implemented routes; it does not expose tenant data or invent unavailable pages |
| **Authenticated operating-loop guide** | Evidence-driven setup → measure → detect → simulate → act → explain sequence on Operations Overview | Every guide state derives from actual tenant meter, reading, monitoring-run, saved-scenario, action, and report-snapshot evidence, with direct workspace handoffs | A checked step means a relevant stored record exists; it does not certify outcomes, savings, performance, or any external workflow |
| **In-app notification centre** | Tenant-scoped inbox at `/app/notifications` consolidating open alerts, failed/partial imports, overdue actions, enabled-schedule health exceptions, and open recovery records | Items are deterministically derived from source evidence; each user has audited read/unread state and a direct workspace handoff | It does not send or confirm email, SMS, push, external escalation, or any other delivery channel |
| **Calendar-aware monitoring** | Optional recurring per-meter local operating windows partition future anomaly histories into operating and outside-configured-hours contexts | Source readings, quality findings, anomalies, alerts, carbon calculations, recommendations, and EcoScore remain retained; anomaly evidence stores its applied context | It does not predict occupancy, infer schedules, suppress off-hours signals, erase evidence, or certify fewer false positives |
| **Campus equipment registry** | Tenant-owned equipment inventory linked to a campus site and optionally to a same-site meter | Create and lifecycle changes are tenant-scoped and audit-recorded; meter linkage is validated against the selected site | It does not establish live telemetry, device health, maintenance completion, performance, or automation |
| **Presenter Mode** | Six-stage authenticated judge flow from tenant boundary through simulation, intelligence, scenario, action/outcome, and report | Each stage routes only to a valid workspace and states its model/simulation/evidence limitation | It is a presentation guide, not a substitute for a configured tenant session or external validation |

## Improvements Requiring a Deployment or External Partner Decision

| Capability | Why it cannot be honestly completed only in the local repository |
|---|---|
| Deployed OAuth/tenant journey | Requires configured production identity callback, application values, user accounts, and user-controlled authentication. |
| Scheduled monitoring | Requires a controlled platform scheduler/cron task, deployment authentication, and observed persisted run/recovery evidence. |
| Invitation email or messaging delivery | Requires selecting a provider, consent/process design, credentials, and delivery verification. |
| Live IoT/BMS/Odoo/utility connection | Requires an approved data owner, field mapping, network/device access, credentials, and a monitored pilot. |
| Certified factors and carbon reporting | Requires recognized factor sources, methodology ownership, approved boundary rules, and review/assurance process. |
| Restore, performance, security certification | Requires deployed backups, measured load/browser testing, and independent security/accessibility validation. |

## Recommended Local Build Sequence

1. Build **Presenter Mode** so the product tells one complete operational story in under three minutes.
2. Add **Scenario Sensitivity Analysis** and a visible **Methodology Drawer** to raise decision credibility.
3. Add **EcoScore Drill-Down** and a **Meter Freshness Board** so every headline number can be explained.
4. Add **Action Ownership, Due Dates, Approvals, and Maintenance Windows** to make operational follow-through credible.
5. Then choose the first external proof loop: one approved meter/feed, a controlled scheduler trial, one responsible user, and a measured intervention outcome.

## The Most Important Improvement

The highest leverage improvement is not another chart or a larger AI model. It is a **realized-outcome evidence loop**:

> **accepted baseline → approved action → measured post-action window → deterministic comparison → disclosed realized/insufficient result**

That feature makes EcoSphere meaningfully different from a sustainability dashboard. It changes the product from “showing possible savings” to “helping a campus learn whether an intervention worked.”
